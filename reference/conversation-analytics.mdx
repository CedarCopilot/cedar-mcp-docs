## Capability

Compute cadence, funnel and pipeline metrics server-side; never tally rows yourself. Use describe-metrics for the metric/groupBy catalog, reducers, units and requirements. ACTIONS: compute-metric with computeMetric:&#123;metric,filter,...&#125;; compute-metric-batch with computeMetricBatch:&#123;items:&#91;&#123;id,metric,filter,...&#125;&#93;&#125; (up to 50 isolated items); describe-metrics. The shared filter cube supports conversationIds, reps, stages and date bounds; omitted conversationIds means org-wide. Rows include value,n,sampleIds; ordinary n:0 becomes null. Live-only crm_won_amount/crm_open_due_amount require filter.reps:&#91;one Cedar user ID&#93;, explicit from/to date bounds and crmReporting:&#123;timezone:IANA zone&#125;. They use provider close dates and mapped amounts, never fall back to Cedar, and separate currencies. Results include verifiedAt and crmDeals with exact Cedar conversation IDs when linked. Verified empty windows return 0; missing amounts return null with knownAmountSubtotal and missingAmountCount. Call live metrics sequentially to respect CRM rate limits. Cedar win_rate/deals_dropped/quiet_gap/hygiene/won_pipeline/avg_acv and groupBy:outcome require outcome:&#123;won,lost&#125;; inspect conversation-read describe-field for status vocabulary. Cedar does not infer terminal status. judged_strength averages taxonomy atom strength for a target field-family glob such as coaching.discovery.*. Other taxonomy counts/distributions and payload aggregations use run-sql; discover available fields with taxonomy-fields.

## Parameters

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `action` | "compute-metric" · "compute-metric-batch" · "describe-metrics" | Yes | compute-metric = aggregate a metric; compute-metric-batch = up to 50 compute-metric calls in one request; describe-metrics = list the metric × groupBy catalog.  |
| `computeMetric` | object | No | Compute an analytics metric over the taxonomy atoms/events, grouped + filtered. Returns rows with value + n + sampleIds — zero client-side math.  |
| `computeMetricBatch` | object | No | Run many compute-metric calls in one request, each isolated: one item failing never fails the rest.  |
| `describeMetrics` | object | No | List the computable metrics × groupBy dimensions (the analytics catalog).  |
| `user_request_summary` | string | Yes | One sentence, in your own words: what the user actually asked you to do in this turn. Used only for Cedar's observability — it does not change what this tool does.  |
| `is_new_request` | boolean | Yes | true on the FIRST Cedar tool call of a NEW user request; false when this call continues the same request you are already working on. Groups related calls into one activity thread.  |

### computeMetric

| Parameter | Type | Required | Details |
| --- | --- | --- | --- |
| `metric` | "crm_won_amount" · "crm_open_due_amount" · "response_time" · "followup_time" · "post_meeting_time" · "reply_rate" · "event_count" · "time_between_stages" · "stage_funnel" · "win_rate" · "aop_conversion" · "deals_dropped" · "quiet_gap" · "gave_up_count" · "hygiene" · "contacts_reached" · "open_deal_age" · "stalled_deal_revenue" · "total_pipeline" · "won_pipeline" · "avg_acv" · "judged_strength" | Yes | The analytics metric to compute server-side (never tally rows yourself).  |
| `target` | string | No | Metric-specific: a fieldId, eventType, a payload key (distribution), "stageA-&gt;stageB" (time_between_stages), a day-threshold override for deals_dropped/quiet_gap/gave_up_count (default 10, the org quiet-gap threshold), a comma-separated subset of company,contact,deal_value,next_step for hygiene (default: all four), or — for judged_strength, REQUIRED — a taxonomy field-id family glob (e.g. "coaching.discovery.*", "coaching.followup.rs*").  |
| `groupBy` | string | No | Group by: rep&#124;stage&#124;field&#124;deal&#124;event_type&#124;email_classification&#124;outcome&#124;month&#124;payload:&lt;key&gt;. Omit → one "all" row.  |
| `filter` | object | Yes | The shared filter cube scoping which atoms/events/deals are aggregated. Omit conversationIds → org-wide.  |
| `outcome` | object | No | Agent-supplied won/lost status values — REQUIRED for win_rate, total_pipeline, and any metric scoped to the open pipeline (deals_dropped, quiet_gap, hygiene, contacts_reached, open_deal_age, stalled_deal_revenue, followup_time), and for groupBy:"outcome" (Cedar infers no terminal status). Get the vocab from describe-field on the status field.  |
| `crmStages` | object | No | Optional CRM stage values per bucket. With it, an org-wide ungrouped win_rate/won_pipeline/avg_acv/total_pipeline is read live from the CRM (row source:"crm_live"); else from Cedar.  |
| `crmReporting` | object | No | Required for live crm_won_amount/crm_open_due_amount: close-date window timezone, e.g. America/Los_Angeles. One filter.reps user and explicit from/to date bounds required.  |
| `perDeal` | "latest" · "max" | No | Deprecated and ignored. It only ever applied to the atom metrics, which moved to run-sql (per-deal normalization is a GROUP BY there, in whatever shape the question needs). Accepted so an existing caller does not fail validation.  |
